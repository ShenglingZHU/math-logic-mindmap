# Layered Acceptance Protocol

## A. Mathematical review: recommended, but not a release gate
When an additional audit file is useful, copy `math-review.example.json` from this directory; it is not a release gate.
Review domains, quantifiers, conditions, theorem applicability and variable mappings, necessity/sufficiency, both directions of equivalence, local-assumption discharge, exhaustive cases, and absence of cycles.
For a nontrivial proposition that requires research, check that `proof_flow` is calibrated jointly by first-principles obligations and the selected authoritative path. The authoritative path controls macro milestones and emphasis; human-first granularity controls expansion inside each milestone. Verify the route choice, reasons for not choosing major alternatives, source quality, fallback record when the network was unavailable, and persisted information in context and relevant granularity reasons. Search results never replace independent mathematical verification or independently justify `proved`.
Numerical evidence and intuition are not strict predecessors, and a counterexample is not a proof of the original statement. Every node corresponds to a milestone recognizable to a reader; a one-off mechanical step normally belongs inside a continuous derivation.
Audit granularity in this order: structural necessities, whether a mechanical stretch deserves any visible node, the existing retention reasons, then a concrete understanding gap for the intended learner. If visible, keep one continuous mechanical stretch in one TRANSFORM; break it when an intermediate result is reused, and merge adjacent stretches when their intervening result lacks an independent reason. Keep an invoked external theorem visible without inventing an application node. Review one-input/one-output advisory candidates by imagining their removal, including the required rewrite of edge details, labels, relations, navigation, and references. A retained candidate needs a specific mathematical reason; advisories are not machine release gates. Resolve the visible nonblocking warning by reviewing candidates and removing stale granularity-review records from the source model before building.
Multiple inputs may enter only COMBINE, which is followed by an independent result. TRANSFORM has exactly one input with all conditions available. Every strict dependency is visible and reaches the unique TARGET. Never create a fact package for port fan-out.
Record a mathematical review summary when useful; per-node and per-edge review files are optional. Machine checks do not prove mathematics automatically. Revise and release again after finding a problem.

## B. Machine gates: block release
- The reading contract is complete: stage coverage, navigation references, input-review and usage-step coverage, and formula-source identity. Missing formal fields are rejected explicitly.
- Every explicit mathematical expression in authored Markdown is inside legal `$...$`. Bare TeX, scripts, function or proposition calls, simple arithmetic and absolute value, formula relations, and mathematical Unicode trigger `MATH-INLINE`. Node titles, `proof_flow` stage titles, justification-box names, Canvas edge labels, and group titles contain no mathematical markup. Authors review every ambiguous `MATH-INLINE-RISK` warning, which receives priority in the CLI summary.
- Continuous main chains are complete: input start, justification rows bound to adjacent before/after expressions, input coverage, local references, symbol-table coverage, and final-expression identity with formal output. Auxiliary calculations are complete inside one justification box, and every formula enters the single table after the chain. Missing or multiply owned content blocks block build and release.
- One-level neighboring-combination summaries are complete; table-alias links parse correctly; long formulas appear below tables; semantic bars, reserved-heading conflicts, and result identity pass checks.
- The schema engine actually runs. Missing dependencies fail rather than being skipped.
- IDs are legal and unique; endpoints exist; the graph is acyclic; there is one TARGET; strict roots have legal types, including a scope-opening local assumption; every strict node is reachable through pure FLOW; COMBINE/TRANSFORM/CASE degree and relation rules hold; local binders, nested scope openings/closures, branch isolation, and declared symbol visibility pass; granularity findings are resolved; non-proof content is isolated; and edge explanation modes are valid.
- Every formula has a structured symbol table; display formulas are not hidden in prose; every condition has a matching check.
- Every symbol-table row contains one notation item. Unambiguous top-level lists fail validation; local ownership and first-column width estimates produce warnings.
- Top-level list scanning covers only unambiguous punctuation and TeX spacing. Ordinary spaces cannot reliably separate notation, so aggregates such as `I f n` remain a human-review item rather than a hard gate.
- Card budgets, static width tiers, minimum estimated dimensions, rectangle non-overlap, downward clearance, and group membership hold. An overwide formula reports an author-wrap suggestion or visual risk only.
- When a structured logical formula is displayed, check that each implication's consequent is indented beyond its premise, each existential “such that” is below and farther in than its binder, and each left-braced list contains left-aligned simultaneous conditions. Preserve existing explicit or implicit universal quantification. The card either shows the full formula within budget or explicitly uses summary mode. Multiline formulas in main chains and edge notes must remain display mathematics.
- Card content matches the model; colors, arrows, labels, and modes agree.
- Model language matches the build configuration. Canvas, notes, checklist, and manifest record the same frozen language and six-color palette. Changing the current global configuration does not change historical topic identity.
- Every generated node and explanatory-edge note exists; explanatory edges are reachable from both endpoint relationship directories.
- Every generated wikilink target file, heading, and node fragment exists.
- The current model, layout, and staged version are unchanged; existing generated regions are never silently overwritten.
- Routes follow the zero- or two-bend `downward-orthogonal` structure, avoid unrelated cards and their 24 px safety bands, share no long collinear segment, and keep centerlines of projected overlapping parallel lines at least 32 px apart. Ordinary crossings are allowed.
- Automatic coordinates prioritize actual route conflicts. COMBINE clustering is optimized only after hard conflicts reach zero. Layout reports distinguish the coordinate algorithm from the routing profile and include COMBINE input-distance, cluster-center, and long-reuse metrics.

## C. Manual Obsidian inspection: optional feedback after release
The `reading_context`, `input_tables`, and `derivation_bases` checks require stages and input/output relations to be readable and reachable, intact tables, unclipped long formulas, and correct justification boxes and results. Old evidence does not acquire new checks automatically. Use `review-template` to produce a new template bound to current files and `presentation_identity`.
`chain_geometry` requires that the justification and main chain share one display block; a long downward arrow sits left of the right-hand justification box and aligns with the relation; the arrow grows for multiline boxes and complete auxiliary work with adequate spacing and no collision; the continuous-chain region has exactly one unified symbol table. Inspect equality, inequality, and logical reasoning separately. An isolated MathJax layout screenshot does not replace real Obsidian acceptance.
The topic parentheses of both single-line and multiline input boxes include the actual `source.node` ID. Independent external theorems and auxiliary calculations do not receive an input ID. Recheck box width, arrow alignment, and clipping after adding IDs.
The default is `UNREVIEWED`. When needed, use `_review-checklist.md` to inspect MathJax, headers, containment, local symbol tables, navigation, layout and labels, scopes, and themes.
Inspect ordinary orthogonal crossings in real Obsidian: horizontal segments bridge clearly over vertical ones, both travel directions arch upward, merged dense crossings do not backtrack, labels move above, below, or along their owning segment, visible bridges are not obscured by labels, and routes recompute after dragging nodes. `layout.svg` shows only actual orthogonal segments and not plugin-derived arcs, so it cannot replace this inspection.
Inspect mathematical special cases in the selected output language: `\\text{}`, `\\boxed`, `\\Bigg\\downarrow`, fractions, absolute values, norms, conditional probability, and table bars.
Actual text is at least 16 px and tables at least 15 px; formulas and tables have no clipping or horizontal scrolling. Inspect three-column input-review tables and four-column symbol tables separately. One MathJax atom may still exceed the first column; an estimated-width warning does not replace observation. Enlarge a card or rewrite a summary when dimensions are unsuitable; never clip mathematics.
Exact original geometry other than deterministic orthogonal routes and crossing arcs has not been restored. Routes must remain visually traceable, and misleading crossings or merges cannot be marked PASS.
After finding a defect, modify and release again. Sampling, environment hashes, and per-check evidence are not required for release.

## D. Identity, staleness, and delivery
A manifest `UNREVIEWED` status only says that no visual conclusion has been recorded; it does not block artifact use.
An independent `math-review.json` is immutable review evidence bound to one `model_hash`; its PASS applies only to that model. Read the manifest or `status.mathematical_review` for the current published mathematical-review state. A hash mismatch must show `STALE`; never rebind evidence by editing only its hash.
The review checklist and manifest are excluded from their own artifact hashes to avoid a cycle.
Releasing after a model, card-content, note, or layout change defaults to `UNREVIEWED`.
After a theme, Obsidian, or plugin version changes, submit acceptance from the new environment instead of reusing the old conclusion.
A tool, CSS, or plugin upgrade changes `presentation_identity`; existing topics may become `STALE` once and should be rebuilt and released with the current version. Changing only the root user configuration does not change a published topic's frozen identity or make its status stale.
`status` compares current artifact and model hashes; a formerly checked box in a checklist is not sufficient.
Validate all staging content before release. Keep backups and restore them after write failures. Preserve personal notes, and block deletion of an orphaned old note that contains personal content.

## Development acceptance
Positive and negative tests cover proof standards/status, schema fields, strict roots and FLOW, granularity, COMBINE, TRANSFORM, paired CASE, explanatory edges, nested scopes, binding freshness/dependencies/uses, existential introduction/elimination, induction obligations, links, budgets, layout import, downward orthogonal routing, Chinese/English/French configuration, frozen colors, and preservation of personal notes across language changes.
Plugin geometry tests may skip in an ordinary Python-only environment without Node. Release-level plugin regression must set `MATH_LOGIC_MINDMAP_REQUIRE_NODE=1`, fail when Node is absent, and finish with zero skips. Performance tests use synthetic edge sets substantially larger than the formal graph budget to cover complete intersection detection and bridge grouping, with ample margin against a 200 ms redraw target.
System tests use only neutral fixtures under `tests/` and read no formal `proof/`, `mindmap/`, or `note/` content. `canonical-smoke` covers the minimum lifecycle; `feature-coverage` covers local scopes, explanatory edges, external support, continuous three-input combination, and wide cards. Routine tests also run the full suite, release, deletion, and same-slug recreation in a temporary system copy with no active topics. Topic deletion covers read-only preview, explicit exact-name confirmation, warnings about manual content, neighboring-slug isolation, preservation of Proof source after partial failure, and same-slug recreation.
`check-skill-sync` checks both generated entry points.
Passing source and unit tests does not mean the Obsidian visual review passed; a sample with an explicit pending-review status may still be delivered.
Ordinary calls do not load tests, docs, or performance history. Detailed reports remain in build assets, while successful feedback stays concise.

# Screenshot troubleshooting
Block release on `ROUTE-NODE-INTERSECTION`, `ROUTE-NODE-CLEARANCE`, `ROUTE-SHARED-SEGMENT`, `ROUTE-PARALLEL-CLEARANCE`, local upward movement, or inadequate bend clearance. Ordinary point crossings are counted but do not block.

Directly repair obstruction, backtracking, or wrong entry confirmed by a user screenshot. Move nodes or change within-rank order first; do not add route bends. Release again once basic checks pass.
